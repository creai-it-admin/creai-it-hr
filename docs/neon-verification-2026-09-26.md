# Neon 전환 검증 — 2026-09-26

## 완료된 범위

운영 수집 CLI는 `.env.local`의 `DATABASE_URL`에 지정된 Neon `hr` 스키마에 저장한다. 스케줄러와 실제 LLM 호출은 추가하지 않았다. 일반 TCP 접속은 이 로컬 환경에서 `ECONNRESET`이 발생했고, 공식 Neon WebSocket 드라이버의 실제 트랜잭션을 이용해 구현·검증했다.

## 원본 데이터 이전과 대조

- SQLite 파일 5개, 공고 행 **520개 → 원본 식별자가 다른 공고 398개**. 플랫폼 간 유사 공고는 합치지 않았다.
- 기존 revision **14개**, 분석 대기 **14개**, 수집 실행 **19개** 보존.
- 모든 원본 공고 식별자 520행·revision 스냅샷 14개·분석 입력 14개·실행 보고서 19개를 실제 Neon과 대조했다.
- 원본은 읽기 전용으로 열었고 그대로 남겨 두었다. 동일 파일들을 재이전하면 `alreadyImported: true`이며 새 행을 쓰지 않는다.
- 변경 이력과 분석 입력의 내용 해시가 맞고, 상세가 있는 모든 공고의 최신 버전과 현재 본문이 일치한다.
- 테스트 데이터는 독립 `hr_test_*` 스키마에서만 생성했다. 최종 감사 시 남은 테스트 스키마 **0개**, 운영 공고의 남은 작업 임대 **0개**.

- `npm test`: **27/27 통과**. 파서·부분 HTML·HTTP 재시도·인코딩·로컬 브라우저.
- `npm run test:db`: **20/20 통과**. 실제 Neon의 중복/수정/기간 변경/마감/부분 실패/오래된 응답/rollback, 세 플랫폼 파서→DB 흐름, SQLite 중복 병합·재실행, 동시 쓰기·임대 만료·분석 재시도/완료, 1만 건 테스트.
- 8개 동시 입력이 동일 공고·버전·분석 작업을 중복 생성하지 않음. 같은 ID라도 다른 source/tenant이면 별도 공고.
- 만료 후 재할당된 공고·분석 작업에 이전 작업자의 성공/실패가 반영되지 않음.
- 분석은 현재 본문이 변경되어도 자신이 참조한 revision의 입력을 읽음.
- 타입 검사, ESLint, Next.js production build 통과.

## 1만 건 마이크로 테스트

실제 Neon의 임시 스키마에서 실행했다. 아래 시간은 이 로컬 환경과 원격 DB 사이의 왕복 시간을 포함하며, 서비스 처리량 보증치가 아니다.

| 항목 | 결과 |
|---|---:|
| 목록 10,000건, 500건씩 20회 UPSERT | 6.67초 |
| 동일 10,000건 재관측 | 4.76초; 공고·revision·분석 작업 중복 없음 |
| 상세 24건 저장, 동시성 4 | 9.15초 |
| 동일 상세 재저장 | revision/분석 작업 증가 없음 |
| 누적 분석 작업 10,000건 중 대기 10건 | 2개 작업자가 5개씩 서로 다른 작업 임대 |

분석 대기열의 누적 이력은 인덱스 검증용 SQL fixture로 생성했다. 이를 1만 번의 실제 상세 수집이나 LLM 실행으로 계산하지 않았다.

`EXPLAIN (ANALYZE, BUFFERS)`에서 `postings_due` 및 실제 분석 claim의 선택 조건에 대한 `analysis_pending` 인덱스 사용을 확인했다. 운영 CLI는 전체 행 COUNT를 매번 수행하지 않으며, 본문을 목록 조회·대기 작업에 복제하지 않는다. PostgreSQL의 자동 VACUUM은 기본 설정을 유지한다. 이 시험은 반복 갱신 직후 상태까지 포함하지만 장기간 지속 부하 시험은 아니다.
