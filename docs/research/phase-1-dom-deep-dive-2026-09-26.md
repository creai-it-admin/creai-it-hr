# 1차 수집 대상 확정 및 DOM 심층 조사

기준일: **2026-09-26 KST** · 상태: 실제 표본 조사와 구현 설계 완료, 수집기 구현 전

## 1. 결정과 조사 범위

**1차 구현 대상은 사람인·잡코리아·인크루트, 정확히 세 곳으로 확정한다.** 다른 사이트는 [이전 10개 사이트 조사](job-sources-2026-09-25.md)에 후보로 보존하고 이번 구현에서 제외한다. 무료 제품의 운영비를 낮추면서 전 직무의 신입·인턴·경력무관 기회를 확보하는 것이 목적이다.

완료 목표는 세 사이트를 한 번 읽는 것이 아니라, **반복 수집해도 중복이 늘지 않고 신규·조건 수정·기간 연장·마감이 구분되어 쌓이는 것**이다. 목록 탐색과 상세 추출만 사이트별로 만들고, 저장·비교·재시도는 공유한다. 전체 구조는 [수집 기획](../ingestion-plan.md)을 따른다.

이번에는 비로그인 브라우저에서 목록 필터·정렬·페이지 이동과 실제 상세 DOM을 읽고, 같은 공개 URL의 일반 HTTP 응답도 비교했다. 비공개 API를 추측하거나 차단을 우회하지 않았다. 공식 API 규격은 9월 25일 조사 기록을 참조하며, 승인된 API 실호출은 아직 하지 않았다.

| --- | --- | --- | --- |

숫자·선택자는 조사 당시 표본의 관측값이다. 전 사이트 완전 수집이나 장기 안정성을 검증했다는 의미가 아니다.

## 2. 전송 방식부터 다르다

브라우저 로그인·쿠키를 재사용하지 않은 일반 HTTP GET 결과다. 사이트별 목록·상세 각 1개와 추가 본문 2개, 인턴 목록 1개를 확인했다.

| 요청 | 관측 결과 | 설계에 반영할 내용 |
| --- | --- | --- |
| 사람인 목록 / 상세 | 각각 HTTP 307, 96바이트, 공고 DOM 없음 | 단순 HTTP 수집 가능으로 분류하지 않는다. 승인 API 우선, DOM 경로는 접근 조건 확정 필요 |
| 잡코리아 목록 | HTTP 200, HTML에 공고 행 존재 | 첫 페이지는 브라우저 없이 파싱 가능. 이후 페이지·정렬 요청은 별도 검증 필요 |
| 잡코리아 상세 | HTTP 200, JobPosting 존재, 원시 HTML DOM에 본문 iframe 없음 | 메타데이터 수집 성공과 전문 확보 성공을 분리 |
| 잡코리아에서 관측한 본문 iframe URL | HTTP 200, 텍스트와 이미지 3개 | src를 실제 확보한 뒤 본문을 읽는 단계는 일반 HTTP 가능 |
| 인크루트 목록 / 상세 / 본문 | 모두 HTTP 200, EUC-KR | 기본 HTTP 파서로 처리. 문자셋 디코딩 필수 |
| 인크루트 상시 인턴 2페이지 | HTTP 200, `ul.c_row[jobno]` 60행 | 오늘 피드 밖의 기존 공고를 GET 페이지 이동으로 발견 가능 |

표본 응답에서는 `ETag`·`Last-Modified`가 없었고 `no-store`/`no-cache` 계열 헤더가 있었다. **304 응답으로 상세 요청 비용을 크게 줄일 수 있다는 가정은 하지 않는다.** 이미지의 캐시 헤더는 별도 문제다. 사람인 307의 구체적 발생 원인은 이번 관측으로 단정하지 않는다.

## 3. 사람인: 공고 범위를 정확히 좁힌 뒤 iframe을 읽는다

근거: [공채 목록](https://www.saramin.co.kr/zf_user/jobs/public/list), [오리온 상세](https://www.saramin.co.kr/zf_user/jobs/relay/view?rec_idx=55115949), [API 검색 규격](https://oapi.saramin.co.kr/guide/job-search), [ID 조회 규격](https://oapi.saramin.co.kr/guide/job-search-id).

### 목록 DOM과 화면 동작

| 대상 | 확인한 선택자 / 값 | 추출·해석 규칙 |
| --- | --- | --- |
| 일반 목록 행 | `#default_list_wrap .list_item[id^="rec-"]` | 상단 광고·추천과 행 내부 유사 공고를 탐색 범위에서 제외 |
| 공고 ID | 행 `id="rec-55115949"`; 제목 링크의 `rec_idx` | 두 ID 일치 검증, 문자열 키 `saramin:55115949` |
| 제목·링크 | `.notification_info .job_tit a[id^="rec_link_"]` | 현재 행의 주 제목만 |
| 회사 | `.company_nm a.str_tit` | 기업 링크의 `csn`은 불투명한 소스 기업 ID; 사업자번호로 해석 금지 |
| 조건 | `.recruit_info .work_place`, `.career`, `.education`, `.salary` | 없는 항목은 null과 누락 상태 보존 |
| 직무 분류 | `.job_sector span` | 태그는 상세 자격요건을 대체하지 않음 |
| 시각·기간 | `.support_detail .date`, `.deadlines` | 상대 등록 시각과 마감 표기를 원문으로 보관 |
| 정렬 | `select#sort`: `RD` 최신순, `MD` 수정순 | `MD`도 목록 행에는 등록 시각이 표시됨. 수정 시각으로 변환 금지 |
| 크기·탭 | `#page_count`: 20/30/50/100; `.btn_tab[data-type="intern"]` | 설정값을 실행 범위에 기록 |
| 페이지 | `button.page[data-page="2"]` | `data-page="11"`은 다음 묶음일 수 있으므로 인접 페이지와 구분 |

수정순·100개·인턴 탭 적용 후 URL은 `?page=1&sort=MD&page_count=100&type=intern`이었다. 2페이지 클릭 후 `page=2&...&isAjaxRequest=y`가 붙었다. **URL이 먼저 바뀌고 행은 잠시 이전 페이지인 상태를 실제로 관찰했다.** 이후 첫 ID가 `55072188`에서 `55064816`으로 바뀌고 100행이 로드됐다.

따라서 `goto/click` 반환이나 URL만으로 페이지 완료를 처리하면 안 된다. 선택한 필터, 현재 페이지 표시, 목록 로딩 완료를 확인하고 페이지별 ID 집합을 기록한다. 순서 변경으로 페이지 간 일부 ID가 겹치는 것은 허용하되, 이동 후 같은 페이지가 반복되는 경우는 완료가 아니라 진행 오류로 남긴다.

이 화면의 ‘전체’는 공채 화면 안의 전체다. 사람인 전체 공고로 확대 해석하지 않는다. 목록에는 ‘접수예정’ 공고도 있어 발견 즉시 지원 가능한 공고로 표시하면 안 된다.

### 상세 DOM과 추출 순서

1. `.jv_header[data-rec_idx="요청 ID"]`를 찾고 가장 가까운 `.wrap_jv_cont`를 현재 공고 루트로 고정한다.
2. 해당 루트의 `h1.tit_job`, `.jv_cont.jv_summary`의 `dt/dd`를 읽는다.
3. `.jv_cont.jv_howto .info_period`에서 시작·마감 시각과 지원 방식을 읽는다.
4. `.jv_cont.jv_detail` 안의 iframe `src`를 가져와 `rec_idx`가 요청 ID와 같은지 검증한다. `iframe_content_0`이라는 고정 번호만 믿지 않는다.
5. 그 iframe 본문에서 텍스트·표·이미지를 함께 추출한다. `.jv_insatong`, 지원 통계·추천 영역은 제외한다.

오리온 표본에서 현재 공고 `55115949` 다음에 **다른 공고 `54907343`의 상세 전체가 같은 문서에 추가됐다.** 페이지 전체의 제목·dt/dd·이미지를 모으면 두 채용 건이 섞인다. 현재 공고의 기간은 `2026.09.23 00:00–2026.10.07 23:59`, 이어 붙은 공고는 다른 기간이었다.

본문 src는 `/zf_user/jobs/relay/view-detail?rec_idx=55115949&rec_seq=0&...`였다. 표 1개와 채용 이미지가 있었고, 텍스트가 길어도 직무 태그가 섞여 있어 전문 확보의 증거가 되지 않는다. 본문 이미지가 주요 요건을 담는 경우 추출 전까지 `image_or_attachment` 또는 `incomplete`로 남긴다.

### 권장 수집 로직

- **기본 경로:** 승인된 API의 `updated_min/max` 구간과 페이지를 순회해 ID·조건·상태를 확보한다. API 문서의 `start`는 0부터, `count`는 최대 110이며 실제 승인 quota와 응답으로 최종 검증한다.
- **변경 감지:** 마지막 성공 수정 경계에 overlap을 둔다. API의 수정 신호는 상세 재확인의 계기이며, 실제 저장 변경은 정규화한 필드 비교로 결정한다.
- **본문 보완:** 제공·이용 범위가 허용된 공고만 현재 ID의 iframe으로 보완한다. API 메타데이터를 받았다고 JD 전문도 확보한 것으로 처리하지 않는다.
- **DOM 대안:** 신입·인턴 등 명시한 목록을 수정순으로 중첩 탐색하고 별도로 기존 활성 상세를 재확인한다. 수정순 순위나 ‘N일 전 등록’으로 성공 수정 경계를 만들지 않는다.

남은 검증: API 승인·실응답·quota 단위, 마감 상태 응답, 상세 본문 접근·재사용 범위. 일반 HTTP 307 문제를 해결한 것으로 간주하지 않는다.

## 4. 잡코리아: 정렬 이동과 내용 변경을 분리한다

근거: [신입·인턴 목록](https://www.jobkorea.co.kr/theme/entry-level-internship), [프리윌 상세](https://www.jobkorea.co.kr/Recruit/GI_Read/50043788), [공식 API 안내](https://www.jobkorea.co.kr/service/api).

### 목록 DOM과 화면 동작

| 대상 | 확인한 선택자 / 값 | 추출·해석 규칙 |
| --- | --- | --- |
| 일반 목록 행 | `tr.devloopArea` | 추천 영역의 링크까지 일괄 수집하지 않음 |
| 주 제목·ID | `.tplTit a.dev-recruit-link[href*="/Recruit/GI_Read/"]` | URL 숫자 `50043788`이 source ID |
| 보조 ID | `button.devAddScrap`의 `data-gno`, `data-gino` | `gno=50043788`, `gino=51664752`가 달랐음. gino로 대체 금지 |
| 회사 | `td.tplCo a.link` | 기업 링크 `/Recruit/Co_Read/C/15494328?...`는 기업 식별 근거 |
| 조건 | `.tplTit .etc .cell` | 경력·학력·지역·형태·급여 등이 가변적. 고정 n번째 셀 파싱 금지 |
| 태그 | `.tplTit .dsc` | 업무 본문과 구분 |
| 시각·기간 | `td.odd .time`, `.date` | ‘점프업’·상대 시각은 변경 근거가 아님. 연도 없는 `~10/10`은 상세로 확정 |
| 정렬 | `#rOrderTab`: 2 등록일, 3 최신업데이트, 4 마감일 | 기본 99는 랜덤 정렬. 기본 상태를 증분 수집에 사용하지 않음 |
| 목록 탭 | `input[name="rlistTab"]`: 0 전체, 24 즉시지원, 27 오늘등록, 26 오늘마감 | 전체 범위와 당일 필터를 구분 |
| 페이지 | `a[data-page="2"]` | 클릭으로 행이 바뀌지만 주소는 유지됨 |

최신업데이트순으로 바꾸자 상단에 ‘점프업’ 표시 공고들이 등장했다. 노출 순서가 올랐다는 사실과 실제 요건 수정은 다르다. 2페이지 클릭 후 첫 ID가 `49906286` 등으로 바뀌었지만 URL은 그대로였고 정렬값 3은 유지됐다.

목록에 GET form이 있어도 실제 페이지 이동의 요청 계약이 GET이라고 입증되지는 않는다. `javascript:;?Page=2`를 그대로 요청하거나 추측한 AJAX 주소를 구현하면 안 된다. **1차 후보는 승인 API, DOM 대안은 검증한 UI 페이지 이동**이다. 정렬·페이지 변경 직후 이전 행이 잠시 남는 현상도 확인했다.

### 상세 DOM과 추출 순서

1. `script[type="application/ld+json"]`에서 `@type=JobPosting`만 고르고 `identifier`와 요청 `GI_Read` ID의 일치를 확인한다.
2. 제목·기업·기간·조건을 읽되 JSON-LD `description`을 JD 전문으로 취급하지 않는다. 프리윌 표본은 103자 정도의 메타데이터였다.
3. `#details-section` 안의 `iframe[title="상세 모집 요강"][data-jobview-section="job_description"]`가 준비되면 src의 `Gno`를 대조한다.
4. 관측한 src `/Recruit/GI_Read_Comt_Ifrm?Gno=50043788&isHiringCenter=false&hideMapView=false`의 본문을 읽는다. 이 실제 URL의 일반 HTTP 응답도 200이었다.
5. `#application-section`에서 접수기간·지원 방식을 읽는다. `#company-section`은 기업 정보이며 `#recommended-section`은 제외한다.

브라우저의 최초 DOM 및 일반 HTTP 상세에는 iframe이 없었고 이후 렌더링에서 나타났다. 따라서 부모의 텍스트가 짧거나 iframe이 아직 없다고 ‘본문 없음’을 확정하지 않는다. iframe의 `data-jobview-content-revision`은 화면 렌더링용일 수 있으므로 공고 수정 버전으로 사용하지 않는다.

프리윌 본문은 표 5개와 이미지 3개의 혼합형이었다. 신세계 표본은 이미지 중심이었다. 현재 공고의 HTML 텍스트를 읽었더라도 이미지 속 자격요건이 빠질 수 있다. 같은 이미지 URL의 반복은 하나의 추출 작업으로 합치되 이미지 URL이 같다는 이유만으로 내용이 영원히 같다고 가정하지 않는다.

### 권장 수집 로직

- **기본 경로:** 승인된 신입공채 API로 목록·메타데이터를 받는다. 서버 IP 등록·고유 호출 URL·제공 범위는 승인 이후 확정한다.
- **DOM 대안:** 최신업데이트순과 페이지 이동으로 ID를 발견한다. 목록은 일반 HTTP 첫 페이지가 가능하나 정렬·후속 페이지 계약이 미검증이므로 브라우저 동작을 비용에 포함한다.
- **상세:** JSON-LD → 현재 ID의 iframe → 접수 섹션 순으로 읽는다. 관측한 src는 HTTP로 처리할 수 있지만, 임의 ID의 iframe URL을 조립하는 것을 검증된 전 사이트 계약으로 삼지 않는다.
- **변경:** 점프업만 바뀌면 `last_seen_in_list_at`만 갱신한다. 조건 서명 변경·상세 재검증 기한 도래 때 실제 상세를 읽고 비교한다.

남은 검증: 승인 API ID와 GI_Read의 대응, API 삭제·마감 의미, UI 뒤의 페이지 요청 계약, 명시적 마감 상세 표본. 호출 규격을 확보하기 전 ‘HTTP만으로 전체 순회 가능’이라고 약속하지 않는다.

## 5. 인크루트: HTML 수집에 적합하지만 ‘오늘’ 목록만으로는 부족하다

근거: [오늘 목록](https://job.incruit.com/jobdb_list/searchjob.asp?today=y), [상시 인턴 목록](https://job.incruit.com/jobdb_list/searchjob.asp?ct=14&ty=1&cd=4), [일반 상세](https://job.incruit.com/jobdb_info/jobpost.asp?job=2609260000102), [마감 상세](https://job.incruit.com/jobdb_info/jobpost.asp?job=2608310000749), [고용24 연동 상세](https://job.incruit.com/jobdb_info/jobpost.asp?job=2507090000503), [RSS](https://www.incruit.com/rss/job.asp?jobtycd=1&today=y).

### 목록 DOM과 화면 동작

| 대상 | 확인한 선택자 / 값 | 추출·해석 규칙 |
| --- | --- | --- |
| 한 공고 전체 | `ul.c_row[jobno]` | `li.c_col`은 한 공고의 하위 셀이지 별도 공고가 아님 |
| ID | `jobno`, `input#JobList_{id}`, 제목 href의 `job` | 서로 일치 확인. 날짜처럼 보여도 문자열 ID |
| 회사 | `.cell_first a.cpname` | `/company/{id}`는 소스 기업 ID |
| 제목 | `.cell_mid .cl_top a[href*="jobpost.asp?job="]` | 현재 행의 주 공고만 |
| 조건·분류 | `.cell_mid .cl_md span`, `.cl_btm span` | 지역·경력·학력·형태와 직무 태그 구분 |
| 마감·수정 표시 | `.cell_last .cl_btm span` | `~10.26`, `(6분전 수정)` 등. 표시 문자열을 정확한 수정 시각으로 위장하지 않음 |
| 페이지 | `?today=y&page=2` 등 실제 href | 검색 필터를 보존해 링크 그대로 진행 |
| 개수 | select의 `articlecount=10…60` 옵션 | 승인 예산에 맞춘 페이지 크기; 최대 옵션 존재가 호출 허용량을 뜻하지 않음 |
| 경력 | `#crr_list`: `crr=1` 신입, `crr=2` 2년 이하 등 | 빠른 필터에 경력무관 항목은 없었음. 신입 필터만으로 목표 범위가 완성되지 않음 |

상시 인턴 목록은 `ct=14&ty=1&cd=4`이고, 4일 전 등 오늘 이전 공고도 있었다. 페이지 링크는 이 필터를 보존한다. 2페이지의 일반 HTTP 응답에서 60개 공고 행을 확인했다. 인턴 외 다른 고용형태를 함께 모집하는 행도 있으므로 ‘인턴 외’ 공고를 누락하지 않는다.

`today=y`는 당일 신규·수정 후보를 찾는 입력이다. 자정 이후에는 전날 수정 후보가 사라질 수 있고 수집 중단 기간도 복구하지 못한다. **오늘 목록 + 상시 대상 목록 + 기존 활성 공고 재확인**을 함께 사용한다. 이전 조사 RSS는 20건만 반환했으므로 후보 추가 용도로만 쓴다.

### 상세 DOM과 템플릿 차이

| 필드 | 기본 추출 경로 | 예외 처리 |
| --- | --- | --- |
| 제목·게시자 | `.top-cnt h1`, `.top-cnt` 안의 기업 링크 | 실제 고용주와 게시자 별도 저장 |
| 전문 | `.jobcview_detail iframe#ifrmJobCont`의 실제 src | 광고 iframe 제외, query의 `job` 대조 |
| 근무지 | `.working_area`의 `.tt` / `.txt.def` 및 본문 | JSON-LD의 헤드헌터 주소와 충돌하면 근무지로 단정하지 않음 |
| 시작·마감 | `.reception .reception_list .intxt`, `.intxt.end .day em` | `.reception`이 없는 템플릿도 존재 |
| 명시적 마감 | 현재 공고 `.reception`의 ‘마감되었습니다.’ 또는 `.top-cnt`의 ‘마감된 공고’ | 사이트 전체 텍스트 검색 금지; 메뉴 ‘마감된 이벤트’가 오탐될 수 있음 |

일반 표본은 본문 표 1개, 이미지 0개로 실제 업무 텍스트를 제공했다. 부모 JSON-LD description은 짧았고 `validThrough`는 날짜만 제공했다. 접수 섹션에는 `2026.10.26 23:59`가 있어 더 정확한 필드의 근거를 따로 저장할 수 있었다.

한국산업은행 `2608310000749`는 `.reception`에 ‘마감되었습니다.’와 `2026.09.14 16:00`이 함께 있었다. 고용24 연동 `2507090000503`은 **`.reception` 자체가 없지만 `.top-cnt`에 ‘마감된 공고’가 있었다.** 본문은 표 없이 `[직무내용]`, `[근무시간 및 형태]` 등의 텍스트로 구성됐다. 표 전용 파서로 만들면 놓친다.

### 권장 수집 로직

1. HTML 응답을 Content-Type/meta의 EUC-KR에 맞춰 디코딩한다. 잘못 디코딩한 문자열로 hash를 생성하지 않는다.
2. 오늘 목록과 범위를 명시한 상시 목록의 실제 다음 링크를 순회한다. ID를 합집합으로 저장한다. 신입·경력무관의 상시 탐색 시작점은 UI에서 추가 확정해야 한다.
3. 신규 ID, 목록 조건 변경, 재검증 기한이 된 공고만 상세 큐에 넣는다. 상대 수정 표기는 보조 신호이며 매분 문자열이 바뀐다고 변경 이력을 만들지 않는다.
4. 상세 HTML에서 iframe src를 얻고 같은 job인지 확인한 뒤 HTTP로 전문을 읽는다. 일반/헤드헌터/외부 연동 템플릿에 같은 필드가 존재한다고 가정하지 않는다.
5. 기존 활성 공고는 별도 기한에 재확인한다. 수집 장애가 하루 이상 이어지면 당일 목록 재개만으로 복구 완료를 선언하지 않는다.

남은 검증: 목표 사용자 범위를 포괄하는 상시 목록 구성, 실제 전체 페이지 종료, RSS 보존·수정 의미, 본문 제공·재사용 조건. 고용24 연동 공고를 발견했다고 고용24 자체를 4번째 직접 수집 소스로 추가하지 않는다.

## 6. 세 사이트가 공유할 delta 처리

### 서로 다른 세 신호를 분리한다

| 신호 | 비교 대상 | 바뀌었을 때 |
| --- | --- | --- |
| `discovery_signature` | 목록의 제목·회사·조건·명시적 기간 | 상세 읽기 우선순위 상승. 본문 변경 확정은 아님 |
| `detail_content_hash` | 정규화한 업무·요건·근무 조건·지원 경로, 확보한 이미지/첨부 내용 | 실제 변경 필드와 revision 저장 |
| `availability_signature` | 원문 상태·접수 시작·종료·기간 유형 | 예정/접수중/기간 경과/마감/재오픈 갱신 |

조회수, 관심수, D-day, 상대 시각, 광고 순위, 점프업, CSS, iframe 렌더링 revision은 내용 hash에서 제외한다. 목록 서명이 같아도 본문만 바뀔 수 있으므로 상세 재검증을 생략하는 영구 근거로 사용하지 않는다.

```text
소스별 목록/API에서 ID 발견
  → (source, tenant, source_id)로 기존 레코드 조회
  → 신규 / 목록 조건 변경 / 상세 재확인 기한 도래: 상세 작업 upsert
  → 그 외: 마지막 목록 발견 시각만 갱신

상세 수집
  → 요청한 공고 ID와 문서 ID 일치 확인
  → 확보한 필드별 유효성 + 본문 품질 검사
  → 이전 유효 값과 비교
     신규: source_posting 생성
     동일: 검증 시각만 갱신
     의미 있는 변화: 필드 갱신 + revision
     부분 실패: 이전 유효 값 유지 + 해당 추출 상태 기록
  → 근거가 충분한 경우에만 기존 opportunity와 연결
```

반복·동시 실행은 DB unique constraint로 보호한다. 늦게 끝난 과거 수집이 새 관측값을 덮어쓰지 않도록 수집 시작/관측 시각도 비교한다. 읽기 실패로 생긴 null은 원문에서 실제 삭제된 값과 구분한다.

### 놓치기 쉬운 경계

- **접수예정:** 시작일 이전이면 `scheduled`; 목록에 있다고 즉시 지원 가능으로 노출하지 않는다.
- **기한형과 상시형:** 날짜만 지난 경우 `deadline_elapsed`, 원문 종료 표시가 있을 때 `closed`. 날짜가 없으면 임의 종료하지 않는다.
- **목록 누락:** 페이지 실패·추천 재배치·일일 필터 때문에 사라질 수 있다. 상세 확인 없이 대량 마감하지 않는다.
- **수정 시각 부재:** 사이트별 표시에 맞춰 재탐색·재확인한다. 공통 비교기는 만들 수 있지만 세 사이트 모두 같은 시각 cursor로 완전한 증분 수집을 보장할 수는 없다.
- **움직이는 목록:** 순회 중 새 공고 유입으로 페이지 경계가 바뀐다. ID 중복은 흡수하고 최근 구간 중첩 및 주기적 전체 범위 대조로 누락을 보완한다. 한번의 순회는 거래 시점이 고정된 snapshot이 아니다.
- **페이지 진행:** 실제 다음 링크/현재 페이지/ID 집합을 기록한다. 같은 ID가 다시 나오는 것만으로 끝내지 않는다. 상한·예산·시간 초과는 `partial`이며 수정 시각 성공 경계를 전진시키지 않는다.
- **출처 간 중복:** 같은 회사명이나 기업 홈 URL만으로 합치지 않는다. 원본 3개는 보존하고 동일 개별 모집 근거가 있는 경우에만 사용자용 기회로 묶는다.

## 7. 구현 착수 순서와 판정 기준

**공통 저장·비교 → 인크루트 HTTP 경로 → 사람인·잡코리아 승인 경로 연결** 순서를 권장한다. 인크루트가 현재 확인한 세 곳 중 HTML 접근·페이지 이동·본문 추출을 가장 적은 브라우저 비용으로 검증할 수 있기 때문이다. 이것은 구현 순서이며 소스 우선순위를 변경하거나 API 승인 전제를 없애는 결정이 아니다.

첫 구현의 최소 표본은 다음과 같다. 실제 관측 표본과 구현 시 만들어야 할 회귀 검증을 구분한다.

| 검증 | 이번 실사 근거 | 구현 완료 조건 |
| --- | --- | --- |
| 목록 순회·비동기 대기 | 사람인/잡코리아 페이지 변경 후 이전 행 잔존 | 이전 페이지를 새 페이지로 저장하지 않음, 예산 종료는 partial |
| 동일 공고 재발견 | 필터 중첩·페이지 재노출 | 반복 수집해도 source posting 수 증가 없음 |
| 현재 공고 분리 | 사람인 한 문서에 여러 전체 상세 | 요청 ID 외의 제목·기간·본문 혼입 0건 |
| 복수 ID | 잡코리아 gno와 gino 불일치 | GI_Read와 검증한 ID만 사용 |
| 본문 형태 | 이미지·표·텍스트 및 혼합 | 이미지 미추출을 전문 확보로 표시하지 않음 |
| 마감 템플릿 | 인크루트 일반형/고용24 연동형 | 두 유형 모두 정확한 종료 판정, 메뉴 텍스트 오탐 없음 |
| 실질 수정 vs 노출 갱신 | 수정순·점프업 관측 | 노출 변경은 revision 없음; 조건·기간 변경 fixture는 revision 생성 |
| 실패·복구 | 사람인 HTTP 307 관측 | 오류로 기존 값 삭제/대량 마감하지 않음; 재시도 후 정상 갱신 |

조건 수정·기간 연장·재오픈을 시간차 실서비스 수집으로 재현한 것은 아니다. 해당 회귀 fixture와 반복 실행 검증은 구현 단계에 남는다. 운영 빈도는 [공통 기획의 요청 예산](../ingestion-plan.md#7-저비용-실행-주기와-작업-예산)과 승인 조건을 적용하며, 이번 조사만으로 수집률·운영비를 확정하지 않는다.

**이 문서가 확정하는 것:** 세 소스의 1차 범위, 관측한 DOM 계약, 소스별 수집 전략, 공유할 변경 감지 규칙. **아직 확정하지 않는 것:** 승인 API 접근 성공, 전체 사이트 커버리지, 장기 수집 안정성, 본문 재사용 허용 범위.
