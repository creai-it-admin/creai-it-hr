# 채용 공고 수집 소스 실사 — 10개 사이트

> **2026-09-26 범위 결정:** 1차 구현은 **사람인·잡코리아·인크루트**로 한정한다. 아래는 당시 10개 후보를 조사한 기록이며, 구현 범위와 우선순위는 [최신 수집 기획](../ingestion-plan.md) 및 [세 사이트 DOM 심층 조사](phase-1-dom-deep-dive-2026-09-26.md)가 우선한다. 나머지 7개는 보류 후보이며 이번 구현에 포함하지 않는다.

조사일: 2026-09-25 · 상태: 구현 전 기술 실사 및 수집 기획

목표는 학생·취준생·주니어가 찾을 기회를 폭넓게 확보하는 것이다. 개발자 공고에 한정하지 않는다. 아래 10개는 당시 조사한 수집 후보이며, 국내 모든 사이트를 망라했다는 의미는 아니다. Greeting의 여러 기업 채용 페이지는 **하나의 소스 계열**로 센다.

## 1. 조사 범위와 결론

**공식 API로 확보할 수 있는 공고를 먼저 수집하고, 부족한 범위를 사이트별 DOM 어댑터로 보완한다.** 공통 파이프라인 설계는 [수집·갱신·중복 통합 기획](../ingestion-plan.md)에 정리했다.

증거 구분:

- **DOM 확인:** 실제 브라우저에서 목록·상세·페이지 이동 또는 추가 로딩을 관찰했다.
- **문서 확인:** 운영사가 공개한 연동 규격을 읽었다. 키 발급이나 인증된 호출 성공을 의미하지 않는다.
- **설계 제안:** 관찰 결과에 근거한 구현 방식이다. 운영 중인 수집기가 아니다.

9개 소스는 목록·상세를 모두 확인했다. 고용24는 메뉴가 POST 이동 구조였고, 목록 직접 진입은 경고창 후 정상 렌더링되지 않았다. 따라서 고용24의 목록 DOM 수집이 검증됐다고 표시하지 않는다. 대신 공개 상세 화면과 공식 API의 목록·상세 규격을 확인했다.

브라우저에 렌더링된 DOM을 확인한 것이므로, 모든 사이트에서 단순 HTTP 요청만으로 같은 내용이 내려온다고 단정할 수 없다. 구현 시 HTTP 표본으로 먼저 확인하고, 필요한 소스에만 브라우저 작업을 할당한다. 전체 페이지 순회, 삭제·재오픈 상태, API 실호출은 이번 실사 범위에서 완료하지 않았다.

## 2. 사람인

**확인 페이지**

- [공채 목록](https://www.saramin.co.kr/zf_user/jobs/public/list)
- [CJ그룹 표본 공고](https://www.saramin.co.kr/zf_user/jobs/relay/view?rec_idx=55049691)
- [Open API 안내](https://oapi.saramin.co.kr/guide/info), [검색 규격](https://oapi.saramin.co.kr/guide/job-search), [ID 조회](https://oapi.saramin.co.kr/guide/job-search-id), [이용 시 주의사항](https://oapi.saramin.co.kr/caution)

**DOM에서 확인한 구조**

- 공고 링크에 `rec_idx`가 있다. 공고 키는 `saramin:55049691`처럼 URL의 ID로 만든다.
- 목록의 `button.page[data-page="2"]` 클릭으로 `?page=2&isAjaxRequest=y`가 열렸다. `data-page="11"`인 다음 묶음 버튼을 단순 다음 페이지로 오인하면 안 된다.
- 상세의 `.jv_header[data-rec_idx="55049691"]`와 그 상위 `.wrap_jv_cont`로 현재 공고를 한정해야 한다. 같은 문서에 **다른 공고 54988990의 전체 상세도 이어 붙어 있었다.**
- 제목은 `.tit_job`, 조건은 해당 공고 안의 `dt/dd` 쌍에서 읽을 수 있다.
- 본문은 `#iframe_content_0`, 주소는 `/zf_user/jobs/relay/view-detail?rec_idx=...&rec_seq=...` 형태다.
- 표본은 본문 이미지와 긴 직무 분류 텍스트를 함께 포함했다. `innerText`가 길다는 이유만으로 자격요건을 충분히 확보했다고 판단하면 안 된다.
- 지원 링크에서 확인한 `https://recruit.cj.net/`은 기업 채용 홈페이지다. 개별 모집 ID가 없는 이 URL로 CJ 공고들을 합치면 안 된다.

**수집 기획**

1. 승인된 API `GET https://oapi.saramin.co.kr/job-search`를 기본으로 한다. `updated_min/max`의 고정 시간 구간, 수정순 정렬, 0부터 시작하는 `start`, 최대 110건의 `count`를 이용한다.
2. 공고 ID, 등록·수정·마감 시각, `active`, `close-type`을 원본 값과 함께 저장한다. `close-type`으로 기한형·채용시·상시 등을 분리한다.
3. 성공한 수정 시각 경계보다 앞선 구간을 다시 읽고 ID로 upsert한다. 기존 공고 상태는 ID 조회로 재검증한다. 복수 ID 일괄 조회 지원은 확인되지 않았으므로 전제하지 않는다.
4. 이번에 확인한 API 계약에는 상세 JD 전문 필드가 없었다. 본문 확보가 필요하면 승인 범위 안에서 정확한 공고 컨테이너와 iframe만 읽는다. 이미지 공고는 별도 추출 상태를 둔다.

**제약과 미확인**

API 키와 이용 승인이 필요하다. 안내 페이지는 일 500회 호출을 설명하지만 주의사항에는 ‘공고 호출 수’라는 표현도 있어, 승인 시 실제 quota 단위를 확정해야 한다. 무료 앱이라고 교육 홍보 목적의 이용·본문 재배포까지 자동 허용된다고 해석하지 않는다. robots 요청에서는 유효한 규칙 텍스트 대신 307/HTML 응답이 나와 규칙 확인이 끝나지 않았다. 관찰한 공채 화면만으로 전 직무 전체가 수집된다고 볼 수 없다.

## 3. 잡코리아

**확인 페이지**

- [신입·인턴 목록](https://www.jobkorea.co.kr/theme/entry-level-internship)
- [신세계그룹 표본 공고](https://www.jobkorea.co.kr/Recruit/GI_Read/49945660)
- [공식 API 안내·신청](https://www.jobkorea.co.kr/service/api)

**DOM에서 확인한 구조**

- `a.dev-recruit-link[href*="/Recruit/GI_Read/"]`에서 공고 ID를 추출한다.
- `a[data-page="2"]`를 누르면 목록은 바뀌지만 URL은 그대로였다. 관찰한 `javascript:;?Page=2`를 실제 GET 페이지네이션 계약으로 간주하지 않는다.
- 상세에 `JobPosting` JSON-LD가 있다. 표본의 `identifier.value=49945660`은 URL ID와 일치했다.
- JSON-LD의 제목·기업·등록일·마감일은 활용 가능하지만 `description`은 짧은 소개였다.
- 전문은 `/Recruit/GI_Read_Comt_Ifrm?Gno=49945660&...` iframe에 있었다. 표본의 추출 가능한 텍스트는 지원 안내뿐이고, 공고 내용은 이미지였다. 같은 이미지 URL도 두 번 등장했다.
- 페이지에 추천 공고와 지원 버튼이 함께 있다. 페이지 전체의 ‘홈페이지 지원’ 버튼을 첫 번째로 집어 지원 URL로 저장하지 않는다.

**수집 기획**

1. 신입공채 API 연동을 우선 추진한다. 공식 안내상 승인 대상 서비스·서버 IP 등록과 고유 호출 URL 발급 구조이므로, **고정 송신 IP를 가진 수집 실행 환경**이 필요할 수 있다.
2. API가 반환하는 식별자와 원문 URL의 GI_Read ID를 대응시킨다. API 데이터의 게시·마감 범위와 삭제 표현을 실제 응답으로 확정한다.
3. API 접근이 정해지기 전 DOM 어댑터는 기술 후보로 둔다. 실제 페이지 버튼 동작으로 목록을 이동하고 ID 집합을 누적한다.
4. 상세는 JobPosting 메타데이터 → 현재 공고 iframe 순서로 파싱한다. 본문 이미지 URL을 정규화해 중복 OCR을 방지한다. 본문을 확보하지 못한 레코드는 `metadata_only`로 남긴다.

**제약과 미확인**

신입공채 API와 일반 API의 제공 범위를 구분해야 한다. 안내의 일반 API 건수 설명에 상충하는 표현이 있어 전체 제공을 약속할 수 없다. 신입공채 API 안내는 별도 범위를 설명하지만 실제 승인 조건은 미확정이다. 상세 페이지의 무단 재전송·가공 금지 안내 때문에, API로 메타데이터를 받는 권한과 전문 재사용 권한을 분리해 확인해야 한다. CSS 해시·스타일 클래스는 수집 계약으로 사용하지 않는다.

## 4. 인크루트

**확인 페이지**

- [오늘 공고 목록](https://job.incruit.com/jobdb_list/searchjob.asp?today=y)
- [베트남 FAE 엔지니어 표본](https://job.incruit.com/jobdb_info/jobpost.asp?job=2609250000131)
- [공식 RSS 안내](https://people.incruit.com/rss/rss.asp)
- [신입공채 RSS](https://www.incruit.com/rss/job.asp?jobtycd=1&today=y)

**DOM·피드에서 확인한 구조**

- 공고 키는 `job` query 값이다. 날짜처럼 생겼어도 문자열 ID로 취급한다.
- `?today=y&page=2`로 실제 다음 목록이 열렸다. 목록에 수정 시각 표시가 있으므로 ‘오늘’ 목록이 신규 등록만 의미하지 않는다.
- 상세 JSON-LD는 있으나 본문 설명은 제한적이다. `#ifrmJobCont`의 `/s_common/jobpost/jobpostcont.asp?job=...`에서 업무·요건 표의 실제 텍스트가 읽혔다.
- 표본의 JSON-LD 위치는 헤드헌터 사무실인 서울 강남이지만 실제 근무지는 베트남 및 분당 관련 내용이었다. **게시자 소재지와 근무지를 분리해야 한다.**
- RSS 이미지 버튼의 DOM에 실제 feed URL이 있었다. 위 신입공채 RSS는 HTTP 200, XML 정상 파싱, 20개 item을 반환했다. item의 링크는 `/entry/jobpost.asp?job=...` 형태였다.
- 같은 `job`이 `/entry/`와 `/jobdb_info/`에 노출되어도 하나의 source posting이다.

**수집 기획**

1. 페이지네이션 가능한 목록을 기본 수집 경로로 삼고 RSS는 신규 후보 발견을 빠르게 하는 보조 입력으로 쓴다. RSS 20건만으로 수집 완전성을 보장하지 않는다.
2. 신입·인턴·경력무관 목록을 초기 범위로 두되, 조건값은 실제 목록 UI에서 확인해 등록한다. 날짜/직군 분할이 필요하면 결과 중복을 ID로 제거한다.
3. 목록의 수정 신호나 신규 ID가 있으면 상세를 갱신한다. 목록에 다시 올라오지 않은 기존 공고도 별도 재검증한다.
4. 게시 회사·헤드헌팅 회사·실제 고용주를 분리한다. 실제 회사가 비공개면 추측하지 않는다. 근무지·요건은 본문과 상단 조건의 충돌을 표시한다.
5. `pubDate`만으로 수정 시각이나 마감을 추론하지 않는다. RSS의 실제 정렬·보존 기간은 운영 전 추가 검증한다.

**제약과 미확인**

RSS가 살아 있다는 것은 전문의 재배포 허가와 같지 않다. 상세의 재배포 제한 안내를 반영해 제공 범위를 확인한다. 현재 확인한 것은 오늘 목록과 신입공채 피드이며, 전 직군 과거 공고의 완전한 backfill은 검증하지 않았다.

## 5. 링커리어

**확인 페이지**

- [채용 목록](https://linkareer.com/list/recruit)
- [신세계 신입사원 공고](https://linkareer.com/activity/351753)

**DOM에서 확인한 구조**

- 실제 목록 URL에 `filterBy_activityTypeID=5`, `filterBy_status=OPEN`, `orderBy_field=RECENT`, `orderBy_direction=DESC`, `page=1`이 붙었다. 2페이지 버튼 클릭 후 `page=2`를 확인했다.
- `a.recruit-link[href^="/activity/"]`와 `.recruit-name`, `.recruit-category`가 공고 카드에 있다.
- 상단 추천/고정 노출과 일반 최신 목록이 함께 있다. 목록 JSON-LD의 ItemList와 DOM 선두 카드가 반드시 같지는 않았다.
- 상세의 `section` 중 `h2`가 ‘상세내용’인 영역과 그 안 `div.responsive-element`가 본문이다. 기업 유형·기간·모집 형태·직무·지역은 `dt/dd`로 읽을 수 있다.
- JobPosting의 `identifier.propertyID`는 **사업자등록번호**, 값도 회사 번호였다. 공고 키는 반드시 `/activity/351753`의 숫자를 쓴다.
- 상세 본문에 계열사 공고 351750·351754·351728 등이 연결된다. 그룹 채용 캠페인과 계열사 개별 공고를 같은 한 자리로 합치면 안 된다.
- 댓글·채팅·프로필도 같은 화면에 있으므로 공고 파서에서 제외한다.

**수집 기획**

1. 최신순 채용 목록을 페이지 단위로 순회한다. 인턴 전용 분류도 별도 discovery scope로 등록해 놓치지 않되 동일 activity ID는 재생성하지 않는다.

- 표본의 h1은 비어 있었다. 공고 제목 컴포넌트와 `og:title`을 대조한다.
- 지원 주소는 `/ko/o/238271/apply`. 지원 화면으로 들어가거나 개인정보·지원서를 수집할 필요가 없다.

**수집 기획**

1. 기업 공식 홈페이지에서 확인한 Greeting 채용관을 tenant registry에 등록한다. 임의 서브도메인 생성·대입으로 찾지 않는다.
2. 키는 `greeting:{tenant}:{positionId}`다. 한 기업의 한국어·영어 페이지는 언어 variant로 연결하고 두 채용 건으로 만들지 않는다.
3. 기업별 목록 URL과 공고 링크 패턴만 설정하고 상세 파서는 공유한다. GS ITM 한 곳을 조사했으므로 모든 tenant가 동일하다고 가정하지 말고, 추가할 때 목록·상세 표본을 검증한다.
4. 목록 규모가 작으면 전체 목록을 주기적으로 읽고 변경 후보 상세만 확인한다. 마감이 다가오는 ID는 별도 재검증한다.
5. 기업 원문은 여러 플랫폼의 공고를 연결하는 좋은 기준이다. 단, 같은 회사 채용 홈페이지가 아니라 **개별 모집 URL/ID**를 사용한다.

**미확인**

GS ITM 외 템플릿·custom domain·페이지네이션 변형은 아직 검증하지 않았다. robots에 sitemap이 안내되고 지원 경로가 제한되어 있었다. sitemap은 발견 보조 수단이며 현행 채용 상태를 보장하는 자료로 사용하지 않는다.

## 12. 접근 조건 실사

아래는 요청 당시의 관찰이다. robots는 수집 경로 선택에 참고하는 규칙이며 본문 복제·재배포 계약을 대신하지 않는다. 실제 수집기 user-agent에 적용되는 그룹과 이용 범위를 배포 전에 확정한다.

| 소스 | robots 조회 결과 | 설계에 반영할 점 |
| --- | --- | --- |
| 사람인 | 307/HTML, 규칙 확인 실패 | API 승인 경로 우선 |
| 잡코리아 | 200, 특정 bot·개인 경로 제한 | 일반 경로 허용을 재배포 허가로 해석하지 않음 |
| 인크루트 | 200, 특정 partner 본문 경로 제한 | 조사한 본문 경로와 제한 경로를 구분 |
| 링커리어 | 200, sitemap 안내 | 댓글·프로필은 수집 대상에서 제외 |
| 원티드 | 403 | 우회하지 않고 연동/접근 조건 미확정으로 기록 |
| 점핏 | 200, 특정 bot·개인/지원 경로 제한 | 공고 외 경로를 큐에 넣지 않음 |
| 랠릿 | 200, sitemap 안내 | 이력서·개인 경로 수집 불필요, 파트너 API 우선 |
| JOB-ALIO | 404 | 규칙 파일 부재를 허가로 해석하지 않음 |
| 고용24 | 200, 여러 공통·개인 경로 제한 | 공식 API 계약으로 수집 |
| Greeting GS ITM | 200, `/ko/o/*/apply` 등 제한 | 목록/공고만 읽고 지원 경로는 탐색하지 않음 |

robots 원문 경로: 각 조사 호스트의 `/robots.txt`. 이번 조사에서 로그인·지원·API 신청·약관 동의·기관 연락·정기 수집 활성화는 수행하지 않았다.

## 13. 당시 구현 우선순위 판단 — 9월 26일 결정으로 대체

당시에는 10개 후보의 제공 범위·유지비를 비교해 다음과 같이 제안했다. 현재 구현 범위는 상단에 명시한 세 사이트이며 아래 분류는 조사 이력으로만 보존한다.

- 전 직무 기반: 사람인·잡코리아·고용24. API로 확보할 수 있는 범위를 먼저 확정한다.
- 핵심 사용자 보완: 링커리어의 신입·인턴, JOB-ALIO의 공공 채용, Greeting의 기업 원문.
- 추가 폭과 품질: 인크루트, 랠릿. 특히 랠릿은 본문 제공 API가 승인되면 구현 비용 대비 가치가 높다.
- 조건부 확장: 원티드·점핏. 현재 브라우저 탐색은 가능하지만 전량 수집 비용과 이용 조건이 확인되기 전 기본 데이터 공급을 의존하지 않는다.

이는 기획 우선순위이며 API 이용 승인이 확보됐다는 의미가 아니다. 승인 절차 중에도 독립적으로 가능한 소스의 파서를 개발할 수 있지만, 접근이 안 되는 소스를 대체 기술로 무리하게 우회하지 않는다.
