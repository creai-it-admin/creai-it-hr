# DB 리소스 효율 검토 — 2026-09-26

이 문서는 변경 전 진단 기록입니다. 이후 적용한 개선과 측정 결과는 [DB 최적화 검증](db-optimization-2026-09-26.md)을 참고하세요. 아래 소스 링크는 현재 구현을 가리키므로 진단 당시와 다를 수 있습니다.

**판정: 정합성과 기본 적재 구조는 갖춰졌지만, 반복 쓰기와 분석 대기열의 자원 사용까지 충분히 최적화된 상태는 아니다.** 이번 작업은 검토와 재현 테스트이며 운영 코드·스키마를 변경하지 않았다.

싱가포르 Neon에서 무작위 `hr_test_*` 스키마를 생성해 공고 10,000건으로 검증했다. 모든 수치는 synthetic 데이터의 측정값이다. 외부 사이트·LLM은 호출하지 않았다. 실행 후 해당 스키마를 삭제했다.

## 1. 완전히 동일한 목록 재시도도 전행 UPDATE와 불필요한 반환을 발생시킨다

근거: [observeMany](../server/ingestion/repository.ts#L36).

공고·관측 시각이 모두 같은 10,000건을 다시 전달했고, 모든 상세 재확인 시각을 미래로 두었다. 재확인 대상은 0건인데 SQL은 **10,000행을 갱신하고 10,000개의 ref를 반환**했다. 반환 행을 애플리케이션에서 모두 버린다.

- 500건씩 20번 실행, 3.82초.
- SQL 결과를 JSON으로 직렬화한 크기 1,396,702 bytes. 실제 WebSocket 패킷 바이트를 측정한 값은 아니다.
- 별도 500건 재시도의 EXPLAIN에서 삽입 0건·충돌 500건·갱신 필터에서 제외된 행 0건을 확인했다.

**개선:** 동일 관측 재시도는 실제 값이 달라질 때만 UPDATE하고, 상세 처리 대상만 SQL에서 반환한다. 일반적인 이후 재관측은 `last_seen_in_list_at` 기록 자체가 목적이므로 전부 생략해서는 안 된다. 기록 주기를 완화하려면 정확한 관측 시각을 보존할지 먼저 정해야 한다.

## 2. 분석 claim의 작업량이 요청 수에 비례하도록 제한되어 있지 않다

근거: [analysis claim](../server/analysis/repository.ts#L22).

현재 pending과 만료된 running을 OR로 묶은 뒤 정렬한다. 실제 claim SQL을 `EXPLAIN (ANALYZE, BUFFERS, WAL)`로 실행했다.

| 대기 작업 | 요청 작업 | 선택 전 읽고 정렬한 후보 | DB 실행 시간 |
|---:|---:|---:|---:|
| 10 | 5 | 10 | 0.395ms |
| 1,000 | 5 | 1,000 | 0.875ms |
| 10,000 | 5 | 10,000 | 5.326ms |

10,000건에서는 순차 스캔 후 정렬했다. 지금의 절대 시간보다 **대기량에 따라 매번 읽는 범위가 커지는 구조**가 문제다. 이전의 '1만 건 중 대기 10건' 테스트만으로 이 경로의 확장성을 확인했다고 볼 수 없다.

같은 SQL의 `exhausted` UPDATE에는 LIMIT가 없다. **claim(1) 한 번에 만료·5회 실패 작업 1,000건을 갱신**했다. 요청한 작업 수의 상한이 정리 작업에는 적용되지 않는다.

**개선:** pending 선택과 만료 작업 회수를 각 인덱스 순서에 맞게 분리하고, 회수·실패 전환에도 배치 상한과 SKIP LOCKED를 적용한다. 인덱스를 무조건 추가하는 것보다 현재 쿼리의 선택·갱신 범위를 제한하는 것이 먼저다.

## 3. 상세 저장은 이미 존재하는 공고에도 추가 INSERT 확인과 여러 왕복을 수행한다

근거: [save](../server/ingestion/repository.ts#L79), [failure](../server/ingestion/repository.ts#L156).

| 경로 | DB 왕복 수 | 관측 시간 |
|---|---:|---:|
| claim → 동일 상세 저장 | 6회 | 512–577ms, 3회 측정 |
| claim → 본문 변경 저장 | 8회 | 817ms |
| claim → 수집 실패 기록 | 5회 | 426ms |
| 분석 완료 기록 | 1회 | 93ms |

약 19KB의 합성 본문을 사용했다. 위 시간에는 로컬↔Neon 왕복이 포함되고 스크래핑·모델 호출은 포함되지 않는다. BEGIN/COMMIT도 각각 왕복 한 번으로 계산했다.

이미 claim한 공고에도 `INSERT ... ON CONFLICT DO NOTHING`이 먼저 실행된다. 변경 시에는 현재 상태·revision·분석 작업 INSERT를 별도 쿼리로 전송하고 동일 본문을 현재 상태와 이력 저장용 파라미터로 두 번 보낸다.

**개선:** 유효한 claim을 받은 경로의 중복 INSERT 확인을 제거하고, 현재 상태·revision·분석 등록을 하나의 데이터 변경 CTE로 묶는다. 현재 행 잠금·오래된 응답 차단·원자적 저장은 유지해야 한다. 부분 응답과 기존 값을 합치는 동작 때문에 본문 읽기를 단순히 없애서는 안 된다.

## 4. 운영 DELETE/보존 정책은 아직 구현되지 않았다

운영 모듈에는 공고·이력·분석 결과를 삭제하는 경로가 없다. 참조 중인 공고를 바로 삭제하면 외래키 제약으로 거부되는 것을 별도 테스트에서 확인했다(`23503`). 이는 무결성 보호이며 성능 오류가 아니다.

synthetic 데이터 한 건을 분석 작업 → revision → 공고 순서로 같은 트랜잭션에서 삭제하는 것은 확인했지만, 이것을 운영용 삭제 기능이 완성된 것으로 해석해서는 안 된다. 장기간 누적되는 이력·분석 결과·실행 기록을 관리할 보존 기준과 상한 있는 정리 작업은 아직 미정이다. 근거 이력을 임의로 지우는 최적화는 적용하지 않았다.

## 유지할 구조와 적용 순서

페이지 단위 UPSERT, 의미 있는 변경에만 revision/분석 등록, 분석 입력의 revision 참조, 최대 4개 연결 풀, 외부 작업 중 트랜잭션을 유지하지 않는 구조는 유지한다. 운영 수집마다 전체 COUNT를 하지 않는 점도 적절하다.

우선 동일 관측의 불필요한 쓰기·반환을 줄이고, 분석 claim/정리 작업량에 상한을 둔다. 그다음 상세 저장 왕복을 줄인다. 보존·삭제는 유지해야 할 근거의 범위를 정한 뒤 구현한다.

UPDATE/DELETE 이후 이전 행 버전의 정리와 재사용에는 VACUUM이 관여하고, HOT 업데이트는 인덱스 참조 열의 변경 여부 및 페이지 여유 공간에 좌우된다. 이 때문에 인덱스 추가나 fillfactor/autovacuum 설정 변경부터 하는 대신 불필요한 UPDATE를 먼저 줄이는 편이 맞다. [PostgreSQL VACUUM 문서](https://www.postgresql.org/docs/current/routine-vacuuming.html), [HOT 문서](https://www.postgresql.org/docs/current/storage-hot.html).
